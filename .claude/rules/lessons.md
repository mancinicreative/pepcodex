## Workflow
- NEVER run 4+ parallel file-editing subagents while the Astro dev server is running on OneDrive. Why: 2026-05-29 rebrand — 4 agents + dev-server file watcher + OneDrive sync exhausted the Windows file-descriptor limit (`EMFILE: too many open files` on tsconfig.json), breaking the dev server mid-run. Fix: stop the dev server before parallel agent swarms (≤3 agents safe without it), restart for verification.
- When staging a themed change, ALWAYS diff each staged file and exclude pre-existing unrelated working-tree edits. Why: same session — a prior `pepcodex.com → www.pepcodex.com` domain change sat uncommitted in SEO schema + api/subscribe + llms*.ts; `git add src/pages` swept them in. Unstaged them so the rebrand commits stayed scoped.
- For a site-wide re-theme, re-point the EXISTING token/class names (glass-card, prose-invert, btn-primary, badge--*, --text-medium, --surface-glass) to the new brand in global.css FIRST. Why: 2026-05-29 — this flipped hundreds of usages automatically; only raw literal utilities (text-white, bg-white/x, purple/cyan) then needed per-file sweeps, making a 500+ file reskin tractable.

## Code Quality
- ALWAYS add security headers (CSP, HSTS, X-Frame-Options) in the first deploy config. Why: Shipped with zero security headers — BLOCKER at Phase 4.
- ALWAYS match Astro output mode to content type (static for content, server for API). Why: Used `output: 'server'` for 886 static routes, wasting SSR.
- ALWAYS use `<link rel="preload">` for web fonts, NEVER CSS `@import url()`. Why: Render-blocking font load degraded FCP by 100-300ms.
- ALWAYS include a skip navigation link in the base layout. Why: Missing skip-link is an accessibility failure.
- ALWAYS add `prefers-reduced-motion` when using CSS transitions/animations. Why: Accessibility requirement.
- ALWAYS deploy breadcrumbs consistently across all layouts. Why: 7/10 layouts missing.
- NEVER expose internal config in health endpoints. Why: `/api/health` leaked Beehiiv key presence.
- NEVER use `Access-Control-Allow-Origin: *` in production. Why: Subscribe endpoint allowed any origin.
- ALWAYS use dynamic routes for enumerated categories instead of hardcoded pages. Why: 3/7 categories had pages, 4 missing.

## Content / citation integrity
- NEVER trust a dossier's cited PMIDs without resolving each against PubMed — verify the PMID actually points to the claimed paper, not just that the number is well-formed. Why: 2026-05-31 — cardiogen.mdx carried 8 fabricated PMIDs across `evidenceChainedBenefits`/`conditions`/`timeline`; every one resolved to a totally unrelated paper (beryllium chemistry, a NICU outbreak, etc.), and the whole "cardiac tripeptide" premise had ZERO PubMed support. These render as live "click to view on PubMed" links, so fake PMIDs actively mislead users. Fix: re-verify all 9 real AED PMIDs via NCBI esummary before writing.
- qa-citations and qa-banned-content BOTH strip frontmatter before scanning — they only check the MDX body. Why: 2026-05-31 — cardiogen's fake PMIDs lived entirely in frontmatter (`keyFindings[].pmid`, `conditions[].relevantStudies`, `timeline[].source`) and sailed past both scripts. The build's `prebuild` check (validate-cross-links + qa-seo + qa-scoring) also does NOT validate that frontmatter PMIDs resolve to real/relevant papers. There is currently NO automated guard against fabricated citations in dossier frontmatter — they must be human/LLM-verified against PubMed.
- When one dossier is found to contain fabricated citations, ASSUME its sibling batch shares the pattern and flag them. Why: 2026-05-31 — cardiogen was generated alongside the full 20-dossier Khavinson bioregulator module (Phases 26–27); vesugen.mdx shows the identical "Khavinson VK et al. <year>" author-year + sequential-PMID + tissue-specific-claim structure. Fabrication is a batch-generation artifact, not a one-off.
- NEVER claim "all citations are fixed" after only the PMID pass — fabricated NCT trial registrations, invented trial NAMES/phases, and placeholder values (N/A/TBD) are a SEPARATE class the PMID guard (qa-pmids) does not catch. Why: 2026-06-27 — owner pushed back ("I thought you went through and fixed all the incorrect papers"). The earlier 591-citation wave + qa-pmids only verified that numeric PMIDs resolve. The newest "pipeline drug" dossiers still carried fake NCTs (alixorexton cited NCT04631991 = a Turkish ophthalmology study; oveporexton invented "ORCHESTRA-NT1 Phase 3" + 4 fake NCTs) that the guard skipped because they aren't numeric PMIDs. Fix: extend qa-pmids to flag non-PMID/placeholder citation values (worklist) + verify EVERY NCT against ClinicalTrials.gov for DRUG-MATCH, not just well-formedness.
- A fabricated NCT is worse than a fake PMID once the render guard ships: src/utils/citation.ts now turns any `NCT########` into a live ClinicalTrials.gov link, so a fake-but-well-formed NCT (e.g. a real NCT for the WRONG drug) renders as an authoritative trial link. Why: 2026-06-27 — verifying NCT-format alone is insufficient; must confirm `get_trial_details(nct).interventions` matches the dossier's drug. Cross-reference peptide-db.com (aggregates every human trial per peptide) per data/.planning/RESEARCH-RESOURCES.md.
- The curated source/researcher list ALREADY EXISTS — read it before designing data-freshness loops or citation sweeps. Why: 2026-06-27 — ran a recon workflow that pointed agents at the codebase + web but missed `.planning/RESEARCHER-CRITERIA.md` (monitor list + evidence×relevance×timeliness decision matrix = the daily-briefing loop's logic) and `.planning/RESEARCH-RESOURCES.md` (peptide-db.com, FDA Bulk Drug list, USADA/WADA, Lilly/Novo IR, BioPharma Dive) + `data/RESEARCH-SOURCES.md` + `data/source-packs/*.json`. Owner had to point them out.
- For paired-trial programs (e.g. REDEFINE-1 vs REDEFINE-2), VERIFY each PMID maps to the CORRECT sibling trial, not just to the right drug. Why: 2026-06-26 — cagrisema.mdx used PMID 40544432 (REDEFINE-2, the T2D trial, Davies MJ) for REDEFINE-1 obesity claims, which actually belong to PMID 40544433 (Garvey WT). Same drug, same journal/year, but different trial, population, and effect size. Also: one cited PMID (34653394) was a Lancet erratum, not the Lau cagrilintide phase 2 trial (real PMID 34798060). And the headline "22.7%" weight loss was topline/interim — the published REDEFINE-1 paper reports 20.4%; corrected the number to match the verified paper.

## Testing & Verification
- NEVER read a chained `cmd > log 2>&1; echo "EXIT=$?"; grep ...` background task's reported "exit code" as the build's exit — the harness reports the LAST command's exit (the grep), not npm's. Why: 2026-06-26 — citation waves B1/aa/ab all had `npm run build` EXIT 1 (InvalidContentEntryDataError) but I read the trailing grep's exit 0 and committed 3 broken builds, falsely reporting "build green." Fix: capture the real exit INSIDE the redirected log (`{ npm run build; echo "REAL_BUILD_EXIT=$?"; } > log 2>&1`) and grep the log for `REAL_BUILD_EXIT=0`. A build that emits a stack trace is NOT green regardless of the wrapper's exit. (Consider porting pepcodex-app's `scripts/check-proof.js` wrapper.)
- When an LLM/agent edits dossier frontmatter, ALWAYS rebuild and confirm Zod schema validation passes — agents invent off-enum values. Why: 2026-06-26 — citation-remediation agents set `keyFindings[].type` to `review` and `cell`, neither in the enum (`human-rct|human-observational|animal|in-vitro`). Root-cause fix: added `meta-analysis`+`review` to the enum (config.ts:165,377) + DossierLayout badge rendering; mapped `cell`→`in-vitro`. The qa-citations/qa-scoring/cross-link gates do NOT catch invalid enums — only `astro build` does.

## Verification surface coverage (2026-07-24 fabrication sweep)
- NEVER write a content/citation verifier against an ENUMERATED list of paths, collections, or field names — walk the tree structurally and treat anything carrying an identifier as in scope. Why: 2026-07-24 the same mistake bit THREE times in one session. (1) `qa-pmids.mjs:14` hardcoded `src/content/peptides`, so `data/source-packs/` and `src/content/blog/` were never verified once — 253 of 265 audit findings lived in the unwatched surfaces, and the site has 12 content collections, not the 4 I first listed. (2) The pack verifier read `sources[]` only; the real bibliography is `coreLibrary` spread over 34 differently-named arrays (`primaryStudies`, `croatianResearchGroup`, `ophthalmology`, `australianVeterinary`, …) holding 412 of 466 records. (3) The trial triage read `pack.trials[]` only; 57 more registrations sat in `coreLibrary.trialRegistries[]`, `clinicalTrials[]`, `stealthBioTrials[]`, of which 31 were fabricated. A hand-maintained list drifts the moment someone adds a new key; the walk does not.
- ALWAYS treat a weak alias/synonym list as a source of FALSE fabrication reports, not just missed ones. Why: matching CT.gov interventions against dossier `aliases` alone produced 26 bogus "wrong drug" hits — every tb-500 Thymosin beta-4 trial (aliases lacked `thymosin beta 4`, `RGN-259`, `NL005`, `Tβ4`), TAK-448 (a real kisspeptin analog), and NCT03856047, which is the genuine cagrilintide Phase 2 trial that CT.gov lists under the development code `NNC0174-0833`. Acting on those would have deleted real trials. Verification-only aliases live in `data/trial-match-aliases.json`, deliberately separate from the dossier's public `aliases` (some entries are related-but-distinct compounds that would be a scientific misstatement if published as synonyms).
- NEVER auto-overwrite a stored label from a registry before proving the identifier points at the right subject. Why: the dominant fabrication pattern here is *real trial name + invented NCT*, not *real NCT + sloppy name*. Blind "CT.gov is authoritative, take its title" would have relabelled a degarelix prostate-cancer study as "Cerebrolysin and Recovery After Stroke (CARS)" — filing a competitor's trial under the wrong peptide AND erasing the evidence the record was ever broken. Overwrite only after drug-match passes.
- NEVER match trial families on an acronym STEM. Why: `REDEFINE CVOT` matched REDEFINE 3, and both `SYNCHRONIZE-1` and `SYNCHRONIZE-CVOT` matched SYNCHRONIZE-2 — three different trials, each a confident-looking wrong answer. A trial family shares its stem by design, so the stem carries nearly no identifying information. Require exact acronym equality including numeric/suffix parts, and veto any candidate whose registered acronym differs from the stored one.
- ALWAYS use PubMed `ecitmatch` (journal|year|volume|firstPage|author) to resolve formatted citations, and ALWAYS re-verify what it returns. Why: many stored citations carry no title at all ("Dhillo WS, et al. J Clin Endocrinol Metab 2005;90(12):6609-6615" — a real landmark kisspeptin paper), so title matching would have deleted them; a full-title `esearch` also fails on paraphrase because PubMed ANDs every term. But ecitmatch resolves on citation COORDINATES, so when those coordinates are fabricated it cheerfully returns a real but WRONG paper — my own repair pass put a dual-energy-CT adrenal imaging DOI on a BPC-157 safety citation. Resolve, then confirm the result against the citation by title overlap OR first-author+year.
- ALWAYS prefer "strip the unverifiable identifier and flag `verified: false`" over deleting a citation record wholesale. Why: in these packs the citation TEXT was usually genuine and only the identifier invented. Deleting destroys real leads (Sikirić in J Physiol Paris, Wang PMID 30116973, Judak PMID 35298973 all exist); keeping the id ships a false authoritative link. Dropping only the id asserts nothing untrue and preserves the lead for re-citation.
- NEVER make a dosing/quantitative field REQUIRED in a content schema. Why: `protocols.studies[].dosesUsed` was `z.string()` (required), so an in-vitro citation with no dose still had to say something — and what it said was "200 mcg/kg via local injection in rat rotator cuff models" for a paper that was cell-culture work, describing a rotator-cuff model that has ZERO supporting papers in PubMed. A required field pressures the writer to invent. Absent must be a valid answer.

## Research discovery (2026-07-25 monthly-scan calibration)
- NEVER treat a PubMed search result set as evidence of relevance — post-filter every hit by checking the peptide is actually named in the title/abstract. Why: when a quoted phrase has no match, PubMed silently degrades to loose term matching and returns a large, confident, entirely unrelated set. A `bronchogen` scan returned 60 papers on OX40-OX40L signalling, daptomycin pneumonia and phage-antibiotic synergy; with a relevance filter it returned 0. Handing an unfiltered result set to a content agent is how fabrication starts — the agent assumes the list is curated.
- NEVER match literature on an alias shorter than ~6 characters without also requiring a domain-context word. Why: same session — `NASA` (an alias of N-Acetyl Selank Amidate) matched a room-temperature maser and a Mars magnetosphere paper; `AED` (Cardiogen) matched Automated External Defibrillators and antiepileptic drugs; `EDL` (Ovagen) matched the extensor digitorum longus muscle; `P21` matched the p21/CDKN1A gene in oncology papers. This applies to the PRIMARY name too, not just aliases — a short primary name deserves no special trust.
- ALWAYS separate discovery from authorship when agents write cited content: a script fetches candidate sources from the registry, and the agent may only choose among what it was handed. Why: an agent that both searches and writes can produce a citation that fits its narrative; an agent that can only pick from registry-fetched items cannot invent one. This is the structural fix for the fabrication class, as opposed to instructing agents to "be careful".
- ALWAYS sanity-check a scan's per-item counts against plausibility before acting on them. Why: an obscure Khavinson bioregulator showing 31 new papers in 30 days is a broken query, not a busy month. Implausible volume is the cheapest available signal that a matcher is wrong.

## Estimand discipline (2026-07-25)
- ALWAYS lead with the PEER-REVIEWED estimand and label the press-release one, never the reverse. Why: 2026-07-25 — three separate GLP-1 figures across the site were the sponsor's *efficacy estimand* (modelled as if everyone adhered) presented as the headline result, while the published trial reported the *treatment-regimen/treatment-policy* figure: SURMOUNT-1 22.5% vs the NEJM's **20.9%** (13 places across 8 files, including a glossary table that paired PMID 35658024 with 22.5%); REDEFINE-1 22.7% vs **20.4%**; ATTAIN-1 12.4% vs **11.2%**. Neither number is fabricated, which is what makes this class dangerous — a fact-check against "did the trial say this" passes. Cross-file consistency (`qa:claims`) is what surfaces it.
- NEVER "correct" a dossier to match a blog post without fetching the source. Why: same session — the orforglipron dossier said 11.2% and five blog files said 12.4%, and majority-rule would have overwritten the correct published figure with the press-release one. The dossier was right.
- ALWAYS escape `<` before a digit in MDX bodies. Why: agents wrote statistical prose as `P<0.001`, which MDX parses as the start of a JSX tag and fails the whole build with "Unexpected character `0` before name" — 5 files, build exit 1, zero pages emitted.
- ALWAYS allow parentheses inside DOI regexes. Why: `[^\s"')\]]+` truncates Elsevier/Lancet ids — `10.1016/S0140-6736(21)01324-6` became `10.1016/S0140-6736(21`, and the gate then reported a real, resolving citation as fabricated. 47 such DOIs are cited here. Capture through parens, then strip only UNBALANCED trailing ones so prose like "(see 10.x/y)" still works.

## Registry query construction (2026-08-06)
- NEVER OR several quoted aliases into one PubMed query — search one alias at a time and union the ids. Why: PubMed silently drops the quotation marks when a quoted phrase has no match and falls back to loose term matching, and inside an OR that compounds without any signal in the response. Six `na-selank-amidate` aliases returning 0, 0, 0, 2, 2 and 0 individually returned **28,694** when ORed together. Three separate scripts had independently written the same OR-join, so the fix lives in `verification/pubmed.mjs` (`searchPerAlias` / `countPerAlias`) and not in three places. Per-alias querying also makes a degrading alias *visible* instead of smearing it across a total — it immediately attributed a 28,692-hit result to `via "NASA"`, the space agency.
- NEVER use string LENGTH as a proxy for how distinctive an alias is. Why: "gastric peptide" is fifteen characters and completely generic; it appears verbatim in ghrelin and motilin papers, so a thin-dossier scan returned 17 confident "relevant" hits for stamakort, every one about ghrelin. Five alias sets had this shape ("brain cytamin", "cerebral peptides", "blood vessel peptides", "pancreatic cytamin", "testis bioregulator"). `matchers.isDistinctive` now requires a token that could identify a compound on its own. This is the mirror image of the short-alias acronym problem — one collides by being too specific a string in many domains, the other by not being a name at all.
- ALWAYS calibrate genericity against DATA, not against a vocabulary list. Why: the hand-maintained generic-token list held "gastric" and "stomach" but not "intestinal", so chonluten's alias "Intestinal peptide" passed and returned 29 papers on vasoactive intestinal peptide, NDNF interneurons and Lactobacillus. A blocklist cannot be complete — this is the same enumerated-list drift that caused the original verifier-coverage failures. `searchPerAlias({primary})` now flags any alias returning far more records than the primary name does: an alias naming the *same* compound cannot return 29 where the primary returns 0. No vocabulary needed, and it catches words nobody thought to enumerate.
- NEVER let a short alias answer a bare COUNT query. Why: `isRelevant` can tolerate a short alias because it reads the abstract and demands a peptide-context word beside it; a `retmax=0` count query has no abstract, so that safeguard silently does not exist and the acronym collisions return in full. Census queries require 6+ characters.
- ALWAYS require the domain-context word to be NEAR a short alias, not merely present in the abstract. Why: "KED" matched "Evolutionary analysis of KED-rich proteins in plants" because the word "peptide" appeared elsewhere in the same abstract. Real usage is adjacent — "the tripeptide KED", "SS-31 peptide". 150-character window.

## Reporting discipline for scans (2026-08-06)
- ALWAYS have a nothing-found result DELETE any earlier worklist for that item, never just skip writing. Why: `monthly-research-scan` wrote per-slug JSON only when findings existed, and both runs write into the same dated directory. After a matcher fix correctly reduced chonluten from 29 papers to 0, the superseded 29-paper file stayed on disk looking current — which is precisely how a scan that found nothing still hands an agent 29 papers about the wrong compound to write up. Absence of findings is a finding and must overwrite.
- NEVER trust "every identifier resolves" as evidence that citations SUPPORT the page. Why: 2026-08-06 — five dossiers (cerluten, stamakort, suprefort, svetinorm, ventfort) have **zero** PubMed records naming them, while displaying real, resolving, topically adjacent Khavinson-school papers: "Peptides and Ageing", "Peptide Regulation of Gene Expression", and on cerluten a clinical trial of **cortexin, a different compound**. Every citation gate on the site passes that content because every identifier is genuine. This is a third integrity class beyond fabricated identifiers and wrong estimands, and no identifier check can detect it — `npm run source:census` asks the separate question "is the subject of this page named in the literature at all" and reports rather than edits.
- NEVER add a parent compound's name as a verification alias for its derivative. Why: same session — "Semax" returns 230 PubMed records and "Selank" 135, but the amidated derivatives return 5 and 2. Counting the parent literature as coverage for the derivative is exactly the cytamin error (real papers on an adjacent compound presented as support for a different one). Only derivative spellings went into `trial-match-aliases.json`.
- ALWAYS re-check a "no literature" verdict against the DISTINCTIVE NAME ALONE before acting on it. Why: high raw hits with zero relevant results is ambiguous between a broken alias set and a compound with genuinely no literature, and those demand opposite responses (fix the aliases vs escalate the dossier). The disambiguation probe resolves it in one call; without it the loop emitted six LEARN flags a human had to resolve by hand. `na-semax-amidate` was a false positive caught this way — it looked unsourceable until "semax amide" returned 5 records.
